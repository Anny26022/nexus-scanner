# Earnings Pulse history

Daily and weekly refresh workflows run `python frontend/earningspulse_history.py` after stock publication, as an optional step. It reuses the existing R2 credentials, bucket, immutable object uploader and download verification. No frontend components or dependencies are added. A source failure does not block the stock data commit.

The first run backfills missing **filing-date calendar quarters** from July–September 2024 through the current quarter. That initial quarter has only partial provider coverage. Normal daily runs fetch the current and previous quarter. Weekly runs pass `--recheck-oldest` to also refresh one least recently checked older quarter. Missing quarters are retried automatically on subsequent runs, so a partial backfill resumes. Older corrections can take a full weekly rotation to appear; this is not a provider change-feed API.

Each fetched quarter retains all returned fields and is split into published and upcoming records. Exact duplicate events are deduplicated by symbol, fiscal-quarter label and filing date (market is restricted to India); conflicting duplicates are rejected. A successful quarter replaces its prior version, allowing corrections and scheduled-event removals. Fiscal quarter labels are distinct from the calendar windows used for fetching. Null values remain null; unavailable Pro fields are not synthesized.

The public entry point is `/data/earningspulse/index.json`. Only this small index is committed to Git. Each `quarters["YYYY-Qn"]` entry contains `checkedAt` and separate `published`/`upcoming` descriptors with a count, URL and SHA-256 of the compressed bytes. Deterministic JSON and gzip (`mtime=0`) produce the same object when records have not changed. Verified files live under the existing R2 `objects/{sha256}.json.gz` prefix; no new Worker route or deployment is needed. Each file contains `schemaVersion`, `source`, `calendarQuarter`, `status` and `records`. The stock app does not automatically download these objects.

Objects are uploaded and download-verified before the index is atomically replaced. Previously published objects are reused. Failed quarters retain their previous index entries and check times; successfully fetched quarters may advance independently. A drop of more than half the published records is rejected for review instead of deleting history. Missing credentials, source failures and publication failures are recorded in `frontend/earningspulse-refresh-report.json`, uploaded as workflow diagnostics. The index's per-quarter `checkedAt` is the freshness indicator, not the stock release date.

The archives are kept outside the pipeline's root `.json.gz` inputs, so their updates neither change stock revision hashes nor create copies in stock backend archives. Existing immutable objects remain available to older indexes, subject to the bucket's object retention policy; this is latest-known provider history, not a point-in-time backtest dataset or a revision log. There is no IndexedDB/localStorage snapshot cache or new browser code.

The source is an observed public Next.js Flight response, not a documented API. The fetcher uses `RSC: 1`, computes week offsets for the requested calendar quarter, retries once, and checks the returned date window, provider failure flag, core schema, finite JSON values and event identities. Security checkpoints, truncated responses and schema changes fail validation. Older price-reaction fields retain the freshness of that quarter's last fetch. Original source records are not treated as independently verified exchange data.

Run `python3 -m unittest discover -s frontend -p 'test_earningspulse_history.py' -v` for collector tests. Live R2 publication starts only after merge and the next successful workflow reaches the optional step; no production objects are uploaded by the PR tests.
