# Nexus Scanner — Frontend and Runtime Guide

Nexus Scanner is an NSE equity research application built with React 19, TypeScript, Vite, TanStack Query, and Tailwind CSS. It combines an interactive screener and IPO catalogue with immutable data releases generated by the repository's Python EDL pipeline.

The application screens the latest **published trading session**, which can differ from today's calendar date. Supported conditions and built-in preset defaults run against precomputed browser snapshots. Custom conditions requiring additional history use the Python evaluator, pinned to the same scanner revision.

This guide covers implemented frontend behavior, local setup, data generation, runtime execution, storage, and production integration. See the [repository guide](../README.md) for the wider pipeline architecture and calculation methodology.

## Purpose and use cases

| User | What they can use the repository for |
| --- | --- |
| Equity researcher | Build repeatable momentum, trend, liquidity, relative-strength, and fundamental screens. |
| IPO researcher | Browse recent listings and screen the selected listing universe with the common condition builder. |
| Analyst | Identify the session and revision behind a result and reproduce it with retained matching inputs. |
| Frontend developer | Extend filter forms, table workflows, snapshot evaluation, and chart-client integration. |
| Data engineer | Publish validated releases and investigate missing or misaligned inputs. |
| Product integrator | Deploy the static application with a historical evaluation service and optional R2 chart origin. |

Nexus supports research and candidate discovery. It does not execute orders, manage brokerage accounts, or provide a trading backtest. Data availability must be evaluated separately from whether a condition matches.

## Implemented capabilities

| Capability | Current state |
| --- | --- |
| Mainboard screener | Visual filters, presets, universe selection, active chips, sorting, and paginated results. |
| IPO catalogue | Listing windows, symbol/company search, sorting, pagination, and screening of selected listings. |
| Boolean expressions | Match All (`AND`) and Match Any (`OR`) in the UI; the underlying contract supports nested groups. |
| Query input | In real-data mode, text goes to the Python compiler. In mock mode, text is not evaluated; the adapter uses the expression tree. Unsupported clauses are rejected without guessed conditions or fallback filters. |
| Symbol lists | Comparison support and a symbol-list component exist; app navigation currently exposes screener and IPO tabs. |
| Workspace persistence | Current preferences, conditions, sorting, universe, IPO controls, and pending text query persist in browser local storage. |
| Named saved screens | A named-screen library is not implemented. |
| Copy TradingView symbols | Copies the displayed equity-results page using `NSE:<symbol>` format. |
| Watchlist | Displays a confirmation toast; no watchlist persistence or external integration exists. |
| Chart data | Payload generation and `screenerApi.getChart` exist; a chart viewer is not wired into the current table UI. |
| Explain service | The real adapter returns a placeholder valid response, not authoritative server validation. |

## Start locally on port 8080

### Prerequisites

- Node.js and npm compatible with the checked-in package lock.
- Python 3.9 or later for pipeline tools and historical screen evaluation.
- Published files under `frontend/public/data/` for real-data operation.
- Matching EDL inputs and history for custom conditions requiring Python evaluation.

A Git clone can contain public snapshots without the ignored raw history caches. Browser-supported conditions may therefore work while historical custom conditions remain unavailable.

### Install dependencies

From the repository root:

```bash
cd frontend
npm ci
```

For Python evaluation, run from the repository root:

```bash
python3 -m venv .venv
source .venv/bin/activate
python3 -m pip install -r "DO NOT DELETE EDL PIPELINE/requirements.txt"
```

Start Vite from a shell with the environment activated so the `python3` executable spawned by the scanner bridge has those dependencies.

### Run, build, and preview

From `frontend/`:

```bash
# Development server
npm run dev -- --host localhost --port 8080 --strictPort

# Production bundle
npm run build

# Local preview of the bundle
npm run preview -- --host localhost --port 8080 --strictPort
```

Run development and preview separately. Open [http://localhost:8080/](http://localhost:8080/). Strict-port mode reports a conflict rather than moving to another port.

The local preview configuration also installs the Python scanner bridge. This is a Vite process feature; copying `dist/` to a static host does not deploy a Python service.

## User workflows

### Mainboard screening

1. Select an available universe: Mainboard, Nifty 50, Nifty 500, or MidSmall 400.
2. Open Filters and choose a preset or custom conditions.
3. Edit parameters and choose Match All or Match Any.
4. Apply conditions and inspect the results. Request changes update the query; Run also refreshes the active release before rerunning.
5. Sort, paginate, and copy symbols from the displayed results page.

The initial workspace uses RVOL between 1.5 and 20 and price above SMA 50, unless saved preferences restore another configuration. Reset clears the selected conditions. Universe membership comes from published inputs, not a live exchange request at screen time.

### IPO catalogue and screening

Choose 30 days, 90 days, six months, one year, or all published listings. Search by symbol/company and sort the catalogue. Its mapped fields are symbol/company, listing date, current price, daily turnover in ₹Cr, market cap in ₹Cr, delivery percentage, sector, and industry.

Matched IPO Decode rows also show the last complete detail refresh in IST and any failed endpoint names. Missing timestamps display “no complete refresh recorded”; catalogue refresh time is not substituted. The detail lane keeps its 18-issue budget, reserving up to four slots for the full retained listed archive. Each lane prioritizes never-attempted and oldest-attempted eligible issues; unused slots go to either lane. Partial refreshes retain cached endpoints and the last complete timestamp, and remain eligible for retry. Saved errors contain endpoint labels rather than request commands or session headers, including when older caches are restored. The catalogue shows complete, partial or failed provider refresh status separately from issue-detail freshness, and file-load failures have a Retry action.

Listing windows are calendar-based and currently measured from the browser's current date; six months is represented by 183 days and one year by 365. This catalogue window is distinct from the scanner's published trading session. Catalogue pages contain 50 rows; main and IPO screening requests use 15 rows per page.

Issue price, listing price, and return since listing are not mapped into the current table. Missing classification displays `Unclassified`. Some absent numeric source fields are currently mapped to zero by the IPO adapter; zero is not independently verified source coverage.

Run evaluates the selected conditions against a custom symbol universe drawn from the selected listings. Screening results use the common equity-results table. Catalogue rows describe listings; results rows describe matches against the scanner release.

### Symbol-list integration

Developers can call `compareSymbols` to normalize and validate symbols against the snapshot, then pass `customSymbols` in a custom-universe request. These capabilities exist independently of whether the symbol-list component is exposed in navigation.

## Conditions and built-in scans

The frontend catalogues define condition IDs, labels, descriptions, parameter types, defaults, and supported inputs. They are compiled into the application rather than fetched from a live indicator-catalogue endpoint.

| Family | Examples |
| --- | --- |
| Trend | EMA/SMA comparisons, persistence, MA stacks, slopes, reclaims. |
| Momentum | Returns, gaps, consecutive up days, momentum bursts. |
| Range/patterns | Inside bars, ATR/ADR, consolidation, contraction, VCP, resistance. |
| Relative strength | Benchmark-relative performance, RS ratings, RS-line highs. |
| Fundamentals | P/E, quarterly growth, supported financial metrics, earnings timing. |
| Liquidity/trading controls | RVOL, turnover, delivery, market cap, price bands, surveillance. |

The offline preset contract contains **45 scans**, version `v1.0.39`. Publication evaluates their defaults before release. Shared restrictions include market cap above ₹1,000 Cr, price above ₹10, and 50-session average turnover above ₹5 Cr. There is no upper market-cap/price ceiling or blanket 2%/5% circuit exclusion.

Descriptions summarize intent; the declarative expression and parameters determine execution. Modifying a preset may require Python evaluation even when its default result is precomputed.

### Calculation essentials

- Returns use trading-session closes: `100 × (latest close / earlier close − 1)`.
- RVOL20 requires the current volume and 20 preceding volumes; the current session is excluded from the average denominator.
- SMA50 needs 50 recorded closes.
- Average turnover is mean `close × volume`, divided by 10,000,000 for ₹Cr.
- EMA persistence defaults to the engine's extreme-based reset rule, rather than requiring every close to remain above the EMA.
- Weekly inside bars use ISO-week aggregates of daily OHLCV. Completed-week mode includes Friday-ended bars and excludes a developing Monday–Thursday week. Holiday-shortened weeks ending before Friday remain conservatively excluded without an exchange-calendar completeness marker. Current-week mode includes the latest week and marks the result provisional.

See the [calculation guide](../README.md#calculation-conventions-and-formulas) and [condition engine documentation](../DO%20NOT%20DELETE%20EDL%20PIPELINE/docs/TREND_CONDITION_ENGINE.md) for exact definitions and missing-data rules.

## How data reaches the application

### 1. Fetch and maintain inputs

The EDL pipeline retrieves and standardizes stock, listing, index, financial, delivery, event, and other supported inputs. History caches supply longer technical lookbacks. Daily and weekly workflows refresh these inputs through validated staging.

### 2. Calculate and validate artifacts

Pipeline gates check schemas, counts, and date consistency. Derived artifacts include canonical stock fields, financial history, relative strength, breadth, and other scanner inputs. Required failures stop normal public promotion.

### 3. Generate charts before cleanup

The chart builder produces compressed per-symbol candles and events while temporary announcement/news inputs remain available. It includes cached candles through the selected session, without an independent four-year cutoff.

### 4. Create the immutable scanner revision

From the repository root:

```bash
python3 frontend/publish_snapshot.py
```

The publisher reads validated EDL artifacts, computes browser metrics and preset outcomes, freezes local Python evaluation inputs, and creates a content-addressed scanner revision.

| Generated location | Purpose |
| --- | --- |
| `public/data/revisions/<revision>/stocks.json` | Immutable snapshot and JSON compatibility path. |
| `public/data/revisions/<revision>/stocks.json.gz` | Compressed snapshot for supported browsers. |
| `public/data/revisions/<revision>/ipos.json` | IPO catalogue for the release. |
| `public/data/revisions/<revision>/release.json` | Immutable release metadata. |
| `public/data/current.json` | Active-release pointer, written last. |
| `../DO NOT DELETE EDL PIPELINE/.scanner_cache/revisions/<revision>/` | Private frozen Python inputs. |

Catalogues under `src/data/` ship with the frontend build; they are not regenerated inside every immutable data directory. Same-session corrections create another revision rather than overwriting earlier data.

### 5. Publish optional chart objects

R2 publication uploads and verifies immutable chart objects. Once R2 configuration is complete, upload/verification failure stops publication. Missing configuration permits a scanner-only release without chart URLs and logs a warning.

Normal validated EDL publication invokes the snapshot publisher automatically. A standalone history repair requires regenerating matching charts and snapshots before its data reaches the frontend.

## What happens at runtime

1. The app fetches `/data/current.json` without reusing a stale HTTP response and validates the release metadata.
2. It resolves the published session/revision and constructs a revision-pinned request.
3. The adapter chooses the advertised gzip snapshot when browser decompression is available, otherwise JSON.
4. A persistent module Web Worker fetches, decompresses, parses, and validates the snapshot.
5. Supported conditions use published metrics or preset outcomes. The engine selects the universe, evaluates expressions, sorts matches, and returns the requested page.
6. An unsupported expression goes to Python with the same revision and session.
7. The adapter rejects backend responses with a different immutable revision.

| Work | Where/when |
| --- | --- |
| Source acquisition and financial normalization | Python pipeline refresh. |
| Selected metrics and default preset evaluation | Snapshot publication. |
| Candles and event records | Chart generation. |
| Decompression, parsing, supported comparisons | Browser worker on first load/run of a revision. |
| Universe selection, sorting, pagination | Browser worker. |
| Historical expressions absent from the snapshot | Python evaluator at request time. |

Not every arbitrary formula is precomputed. The architecture avoids repeating default preset calculations in every browser while retaining Python support for richer history-dependent rules.

### Freshness and revision changes

The app checks the active release every 60 seconds and on window focus. The main screener's Run action also refreshes it. Revision identity keys requests and caches; the IPO component is remounted when the active revision changes.

This detects **published release changes**, not individual upstream changes directly. Inputs become visible only after pipeline fetch, validation, and publication. Polling does not guarantee a newer session when publication has failed.

### Match states and diagnostics

The engine distinguishes match, no match, and unavailable. Missing required data cannot create a positive match. Boolean groups propagate unavailable where it affects the outcome: match OR unavailable is a match; no-match OR unavailable remains unavailable.

Responses can carry session metadata, match/universe counts, warnings, and unavailable diagnostics. The UI does not necessarily display every field. Coverage fields can be empty; their presence in a type does not guarantee populated analytics.

## Actual adapter and API behavior

`src/api/screenerApi.ts` is a typed real/mock facade. **Its methods are not a list of deployed HTTP endpoints.**

| Method | Real adapter behavior |
| --- | --- |
| `getCatalog()` | Returns the compiled condition catalogue. |
| `getCurrentRevision()` | Reads `/data/current.json`. |
| `runScreen(request)` | Runs the snapshot engine, then `POST <base>/screens/run` if unsupported. |
| `getIpos()` | Fetches and maps the active immutable IPO URL. |
| `compareSymbols(request)` | Runs a symbol comparison task against the browser snapshot. |
| `getChart(symbol, revision?)` | Loads a chart using the release URL template. |
| `explainScreen(request)` | Builder labels are local; Python fallback responses may include runtime availability diagnostics. |

Do not assume `/v1/catalog`, `/v1/ipos`, or `/v1/screens/explain` exist because related facade methods exist. UI explanation utilities are separate from the placeholder explain method.

### Local Python bridge

Vite handles `POST /api/screens/run`, starts a persistent `python3` worker, and exchanges request/response messages through standard streams. Python retains numeric history caches for reuse. The development server restarts the worker when watched Python sources change; preview does not watch those sources. Local server requests have a 120-second timeout.

This development/preview middleware is not a separately packaged production backend. External deployment must supply a service process and the matching evaluation inputs.

## Charts and event data

Call `screenerApi.getChart(symbol, revision)` to fetch one payload. Supplying a revision aligns it with a selected scanner result. The client checks release identity, symbol, and session.

| Chart data | Scope |
| --- | --- |
| Candles | Available OHLCV through the release session. |
| Highest/lowest-ever volume | Across available cached history; not guaranteed inception coverage. |
| Monthly highest-volume records | Latest 60 represented months. |
| Quarterly highest/lowest-volume records | Latest 20 represented quarters. |
| Yearly highest-volume records | Latest 10 represented years. |
| Corporate actions and earnings | Available records satisfying the release cutoff. |
| Regulatory announcements | Available official records. |
| Market news | Latest 50 available items. |

Optional arrays can be empty. `historyStartDate` describes actual candle coverage. A short local cache produces a short chart even if another runner has longer history.

The current application does not draw these charts. A viewer must add rendering, event markers, selected-symbol handling, and loading/error states. Fetch the requested symbol instead of downloading every chart.

R2 retains daily revisions for 90 days and archives the prior month's latest successful release on rollover. Monthly archives are retained indefinitely. Long publication outages can allow daily objects to expire before archival. See the [R2 publication guide](../docs/r2-chart-publication.md).

## Caching and preferences

| Cache/state | Behavior |
| --- | --- |
| TanStack Query | Request/result caching; default stale time five minutes, with a separate frequently refreshed revision query. |
| Worker snapshots | At most two loaded revisions; failed loads are evicted for retry. |
| Matching/sorted sets | Up to four cached result sets per snapshot, reused for later pages. |
| IPO snapshots | At most three revision loads; failures are removed. |
| Local storage | Current preferences under `nexus-scanner.*.v1` keys. |
| Python history cache | Evaluator acceleration, separate from browser state. |

Worker tasks have a 60-second timeout. A timeout rejects that request without terminating other pending tasks. If `Worker` is absent or construction fails, the same engine runs on the main thread with timeout/retry handling. This fallback can affect UI responsiveness during parsing or computation. No WebAssembly runtime is required.

Persisted preferences include the active tab; screener universe, conditions, match mode, and sort; and IPO listing window, search, conditions, match mode, and sort. They are origin-specific, are not uploaded, and disappear when site storage is cleared. Another domain or port has separate storage.

Market snapshots are compressed JSON files. Workspace preferences use local storage. There is no IndexedDB saved-screen database or account synchronization.

## Configuration and deployment

### Frontend settings

For local real-data operation, use `frontend/.env.local` if explicit settings are needed:

```env
VITE_USE_MOCK=false
VITE_API_BASE_URL=/api
```

| Setting | Meaning |
| --- | --- |
| `VITE_USE_MOCK` | Exactly `true` selects mock development data; otherwise the real adapter is used. Mock mode has no charts. |
| `VITE_API_BASE_URL` | Historical fallback base; `/screens/run` is appended. Defaults to `/api`. |

`VITE_*` values are public build-time configuration. Production changes require rebuilding. R2 credentials belong to the server-side publisher and Actions environment, never the frontend bundle.

The manifest supplies chart URLs. Changing the API base does not change `/data/current.json` or automatically configure chart storage.

### Static frontend deployment

Build with `npm ci` and `npm run build`, then host `dist/` with its public data files.

- Deploy immutable files before updating `data/current.json`.
- Revalidate the pointer and reuse immutable URLs through HTTP/CDN caching.
- Keep the plain JSON compatibility path alongside gzip.
- Verify gzip transport: the client supports raw compressed bytes and responses decoded through HTTP `Content-Encoding: gzip`.
- Deploy compatible application/catalogue and data versions.

### Historical evaluation deployment

A static-only installation supports browser-evaluable conditions and preset defaults. For richer expressions, supply `POST /screens/run` under the configured API base or proxy `/api/screens/run` to a Python service.

The backend needs the requested frozen revision, condition implementation, and sufficient matching history. Copying only browser files is insufficient. Service deployment must provide process management, request limits, cross-origin CORS where needed, and monitoring. Vite middleware is not included in the static output.

### Optional chart deployment

Publish through the shared R2 publisher and permit browser access from the app origin. Scanner-only releases have no chart URL template. Report chart unavailability instead of silently using unrelated older data.

## Local history recovery

Git does not contain full raw OHLCV, delivery, or filings caches. Actions cache speeds up runners but can be evicted. Durable private R2 raw-history backups and automatic restoration remain planned; derived chart files are not a complete raw backup.

From the repository root:

```bash
cd "DO NOT DELETE EDL PIPELINE"
python3 sync_local_scanner_history.py \
  --source-root /path/to/existing/EDL \
  --from-date 2026-09-29 \
  --as-of-date 2026-09-30
```

Use dates appropriate to the missing range. The source must be a separate compatible EDL directory with identity mappings and history files. The tool checks ISIN identity, merges history, applies official daily data, and writes `local_scanner_history_report.json`. For later bounded daily recovery, omit `--source-root` and specify the missing range.

After validating that artifacts agree on the release session:

```bash
# From the pipeline directory
python3 build_chart_artifacts.py
cd ..
python3 frontend/publish_snapshot.py
```

The full pipeline handles this ordering automatically. Do not advance the pointer from mixed-session stock, financial, delivery, or chart inputs. Newly listed stocks may still lack long lookbacks after recovery.

## Testing and troubleshooting

### Verification commands

```bash
# From frontend/
npm test
npm run build

# From the repository root
python3 -m unittest discover -s frontend -p 'test_*.py' -v

# Pipeline tests, from the pipeline directory
cd "DO NOT DELETE EDL PIPELINE"
python3 -m unittest discover -s tests -v
```

Tests verify contracts against fixtures. They do not establish complete live upstream coverage for every stock.

| Symptom | Inspect |
| --- | --- |
| Port 8080 unavailable | Another process owning the port. |
| Real-data app fails to load | Pointer, immutable files, schema/revision metadata, deployment completeness. |
| Presets work but custom history rules fail | Python dependencies, API base, frozen revision, history coverage. |
| Insufficient history | Recorded sessions and warmup, especially for recent IPOs. |
| History not aligned | Last cached date versus published screen session. |
| Missing delivery spike results | Historical delivery observations, not just current percentage. |
| Unexpected restored settings | This origin's local-storage preferences. |
| Chart unavailable | Enabled release, retained object, CORS, gzip, symbol/session identity. |
| Missing news/earnings markers | Acquisition, cleanup ordering, event cutoffs, actual source coverage. |
| Old published session | Pipeline status and deployed pointer, not just browser polling. |

## Limits and operating assumptions

- Normal UI screening targets the latest published session; no general historical date selector is exposed.
- Revision-pinned historical evaluation requires retaining corresponding backend inputs.
- Intraday turnover cannot be reconstructed from daily OHLCV alone.
- Current financial/classification snapshots cannot reconstruct all historical point-in-time facts.
- Inception coverage must be checked per symbol; a weekly run is not proof of complete history.
- Other providers may use different universes, adjustments, rankings, and proprietary formulas. Identical labels do not guarantee identical outputs.
- Missing inputs must remain distinguishable from valid zero values and failed conditions.
- Missing R2 configuration allows scanner-only publication; configured upload failures stop publication.
- Chart viewers, named saved screens, durable raw-history recovery, and persistent watchlists need further integration.

Read the [repository guide](../README.md), [data limitations](../DO%20NOT%20DELETE%20EDL%20PIPELINE/docs/DATA_LIMITATIONS.md), and [R2 publication guide](../docs/r2-chart-publication.md) for wider operational detail.
